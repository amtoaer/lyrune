# 代码结构与维护约束

重构采用 `1320e5d`（v1.5.0）的行为基线，没有引入 PR #35 的功能。模块拆分后继续做局部写法和重复逻辑整理，保持设置格式、缓存策略、任务生命周期及用户可见行为。

后续经单独授权，设置保存改为后台顺序写入和原子替换；原有保存触发点及 JSON 格式不变，文件更新会晚于 UI 提交请求。以下持久化说明以当前实现为准。

## 从哪里开始读

程序入口是 [main.rs](../crates/lyrune/src/main.rs)：创建 GPUI 应用和窗口，连接托盘、单实例和 Linux 媒体控制。[app.rs](../crates/lyrune/src/app.rs) 定义 `LyruneView`，创建控件和订阅，组合主界面。

`app/` 中的 `impl LyruneView` 都作用于同一个 GPUI 实体。实体持有领域状态和控件，方法按职责放置；关闭窗口后，主程序仍可持有这个实体，继续播放。拆分状态所有者时，需要同时考虑窗口重开、订阅和后台任务的寿命。

前一轮已由 `playback::PlaybackLoad` 归拢音源加载的请求版本、队列索引和自动播放意图。本轮允许重新划分内部状态与生命周期所有权，同时保留 GPUI 实体和窗口的现有寿命语义；实施清单与验证记录见 [refactor-progress.md](refactor-progress.md)。

已有底层边界继续保留：`player.rs` 管音频设备与解码，`cache.rs` 管音频缓存与流，`http.rs` 管图片缓存，`settings.rs` 管设置和持久化数据格式，`credentials.rs` 管系统钥匙串，`library.rs` 管列表/表格 Delegate。QQ 协议实现仍在独立的 `lyrune-api` crate。

工作区现由三个内部 crate 组成：`crates/lyrune` 是桌面应用，`crates/lyrune-api` 是 QQ 音乐协议实现，`crates/lyrune-decrypt` 负责 QMC 音频解密。包名与目录名一致。

`lyrune-api` 根入口选择性导出应用需要的能力；`account.rs` 持有凭据会话与扫码/刷新编排，`models.rs` 保留共享数据类型，`client.rs` 实现曲库、搜索、歌词、音源及 CDN 请求。扫码与刷新直接调用 `login.rs`，响应校验和 MQTT 状态机位于 `login/`，协议标识和签名算法位于 `request.rs`。网易云、跨平台 builder、平台 token 包装，以及应用未使用的旧查询接口已移除。`QqCredential` 和 `LyricResult` 的序列化字段保持原样；登录 Cookie 和 GUID 继续使用原来的规则。

## 关键调用关系

1. `LyruneView::new` 创建控件、接入事件，然后恢复账号。账号可用后加载首页和音乐库；音乐库加载还会触发已保存队列的恢复。
2. 导航先建立目标页及其资源，再记录当前页、应用目标页。搜索、歌手页面的请求完成后，由 `SearchResource` / `ArtistResource` 应用结果并结束相应加载状态；回调在释放资源锁后，按资源身份决定是否更新当前控件。资源方法不操作 GPUI，也不判断当前页面。
3. 歌单页和歌手页选曲共用 `select_playlist_track`，统一判断复用队列、切换暂停或建立新队列；搜索结果仍按独立规则插入当前歌曲之后。随后调用 `start_playback`，Tokio 任务通过 `prepare_playback_stream` 复用或重新解析音源，再到阻塞线程准备解码器；GPUI 回调检查播放版本后才调用 `AudioPlayer::replace`。
4. 后台 tick 读取音频进度、判断曲终、保存播放状态并同步系统媒体控制。歌词显示另有按设置帧率运行的动画回调。

`LyruneView::playback` 持有播放会话；滑块、悬停预览和音质菜单仍是视图状态。会话内的 `PlaybackLoad` 统一维护请求版本、版本检查和加载标记清理。`invalidate` 只使旧结果失效，`clear` 只清除加载索引与播放意图，保留版本；退出账号时不能用默认值替换整个会话或加载对象。调用处保留以下顺序：

| 触发 | 加载状态与外部操作的顺序 |
| --- | --- |
| 开始播放、切歌或切音质 | 停止设备、请求歌词 → 递增版本 → 设置当前和加载索引 → 检查喜欢状态 → 写入自动播放意图 |
| 加载完成 | 检查版本 → 清除加载标记 → 装入音源，或按原错误路径提示并跳歌 |
| 停止播放 | 递增版本 → 停止设备 → 清除加载标记 |
| 退出账号 | 递增版本 → 停止设备 → 撤销凭据、清理页面和队列 → 清除加载标记 |

## 容易误改的约束

### 账户任务的边界

`Account` 拥有账户状态、凭据句柄、资料、二维码、登录版本和文案。它管理发起登录、失效、会话身份和撤销规则；`account.rs` 中的视图方法负责串接协议、钥匙串、其他领域和 GPUI 通知。登录状态与凭据安装仍按同一次视图更新中的原顺序完成。

| 任务 | 启动与结果处理 | 失效/结束规则 |
| --- | --- | --- |
| 恢复凭据 | 构造后一次启动，Tokio 阻塞线程读取；成功后安装会话并加载首页和音乐库，无凭据/失败时进入二维码登录 | GPUI 实体销毁后无法应用；保留原启动流程，不新增版本或取消策略 |
| 二维码登录 | `Account::begin_login` 阻止恢复中或登录中重复发起；事件更新二维码/文案，成功安装会话，过期自动重试，失败等待点击 | 结果应用前比较登录版本；成功/过期/失败后结束当前事件接收循环；Tokio 任务不因丢弃句柄而取消 |
| 凭据刷新监听 | 安装会话时先订阅，再保存当前快照；刷新后保存新快照，撤销后清理账户并提示 | 登录版本与句柄身份同时匹配；同账号的新会话也会使旧监听失效；当前会话 snapshot 为空时仍必须接收撤销通知 |
| 缓存凭据验证 | 使用缓存音乐库时进行 30 秒限时验证，仅失败时提示 | 版本和会话身份匹配且 snapshot 仍有效时才提示 |
| 保存/删除凭据 | 保存捕获快照，删除在退出清理末尾启动；均通过阻塞线程执行 | 保留原独立后台任务与错误通知，不新增写入排序或版本过滤 |

### 控件、设置与长任务

`SettingsInputs` 拥有设置输入框及默认值、掩码和校验，`set_fonts` 仅回填三个字体输入框。“恢复默认”先改输入框，“应用字体”才更新字体、主题、排版缓存并提交保存。其他设置仍各自按原顺序读值、生效、提交保存和通知。

`LyruneView` 持有唯一的 `SettingsWriter`，UI 将 `AppSettings` 快照发送到 FIFO 队列，不防抖或合并。保存任务逐条等待 `spawn_blocking` 完成；`SettingsStore` 消费快照，规范化、序列化后写入同目录临时文件，再用 rename 原子替换正式文件。保存途中进程终止不会截断已提交的配置；残留临时文件不参与启动读取，下次保存时覆盖。磁盘回写交给操作系统，不使用 fsync，不承诺断电后的持久性。保存错误仍沿用原来的忽略策略。

`LyruneView::new` 创建领域状态、控件和订阅，随后 attach window、报告初始化错误、启动音频缓存/CDN 维护、恢复凭据、按设置安排更新检查。保留订阅句柄使回调持续有效，窗口观察句柄只在 `attach_window` 替换。补页事件接收器跟随实体；表格导航事件接收器使用原 `spawn_in` 窗口寿命，未借重构重新定义窗口重开行为。

CDN 维护和音频缓存维护由视图保存 JoinHandle，重启维护或 Drop 时 abort。CDN 成功刷新后仍通过阻塞线程保存，失败仍按原间隔重试。更新检查延时启动并重新读取开关/进行中状态；完成后按原“手动/自动”区别通知。通知经当前记录的窗口句柄 defer，未改为跨窗口队列。

退出回调调用 `shutdown`：先提交播放快照、停止音频，再提交其余偏好，关闭发送端并等待保存队列排空，最后 abort 两项维护。第一步可能因无账号/当前曲或快照没变化而不保存，所以不能删除第二次保存。等待放在退出回调返回之前：GPUI 对退出 future 的等待仅有 200ms，macOS 终止也不保证返回 main。工作线程不访问 GPUI，不依赖 UI 继续轮询。Drop 复用同一清理入口；已取走的写入者和设备不会再次保存或停止。关闭窗口留在托盘时不会结束写入者。

### 浏览状态和请求边界

搜索、歌手、首页和歌单各自的 `*PageState` 保存当前页选择、可见数量或加载状态。它们没有自己的任务句柄；GPUI 实体在各页面模块编排任务。`NavigationPage` 是历史快照，保存资源强引用而不复制请求结果；控件仍由视图持有。页面切换只清除原来会清除的字段，不用整个页面 Default 代替，以免丢失历史选择或重用版本。

搜索/歌手请求先更新共享资源，再比较当前页资源的 Arc 身份；离开页面不取消请求。歌单页面与播放补全通过既有 SingleFlight 共享请求，资源的 offset 规则拒绝重复回填。库目录和首页请求分别比较自己的版本；喜欢操作继续比较账号 ID。缓存保存策略、错误状态和这些过滤条件均不统一成通用框架。

### 歌词任务的边界

`LyricsCache` 管磁盘句柄、已采用内容、待采用内容、正在加载和错误状态。`ensure_track_lyrics` 先按原 TTL 与加载集合去重；后台任务经容量 2 的通道依次发送磁盘和网络事件，GPUI 调用 `LyricsCache::apply` 后通知。缓存按歌曲 mid 共享，不随退出账号或离开页面清空，不新增会话版本过滤。

旧磁盘内容可先显示，失败不覆盖已有内容；正在播放且已有内容时，不同的网络内容暂存，相同内容只更新时间并保留原 Arc。`adopt_pending` 在开始请求前、该曲尚不是当前曲时调用；切同一歌曲或切音质不强制替换时间轴。原始磁盘保存仍先于 Network 事件，排版和帧面板仍由 `lyrics_view` 管理。

### 播放任务的边界

`Playback::replace_queue` 使旧队列补页和推荐周期失效，不改变音源版本；随后播放入口按原顺序停止设备并开始音源请求。搜索插队沿用原队列版本，仍允许正在进行的补页追加。`Playback::snapshot` 负责恢复数据的内容，视图保留原来的保存触发点并提交快照到后台写入队列。加载中或尚未开始时使用显式恢复位置，设备时钟可能还对应上一音源。

| 任务 | 结果与结束规则 |
| --- | --- |
| 音源准备 | Tokio 解析/复用音源，阻塞线程准备解码器；GPUI 接收事件先检查音源版本，再替换设备。失效仅拒绝结果，不取消后台准备。 |
| 歌单补全 | Tokio 请求可先更新持有的页面资源；GPUI 检查队列版本后才追加当前队列。 |
| 推荐补充 | 按续播类型请求，结果检查队列版本；预取标记与队尾等待标记分别决定加载和接续播放。首批推荐类别过滤的既有风险另案记录。 |
| 窗口 tick | `spawn_in` 跟随窗口；更新控件与歌词帧，窗口重开时重新接线。 |
| 后台 tick | `spawn` 跟随应用实体；窗口关闭后仍判断曲终和保存，暂停时通过通道唤醒。 |

MPRIS 在音源加载期间沿用 `Playing` 状态；它与 `Playback::is_advancing` 描述的设备实际推进不同，不能合并成一个播放布尔值。

### 跨领域不变量

- **浏览状态与播放状态独立。** `playback.current_track`、`playback.load.track` 是播放队列索引；页面选中行不能直接当作队列索引。插入搜索歌曲会标记 `queue.modified`，此后不能仅凭原歌单 ID 复用队列。
- **队列追加保留已有歌曲。** `PlaybackQueue::append_tracks` 按 `mid` 去重，保留已有歌曲的位置和元数据；只返回第一首新增歌曲的索引，重复批次返回 `None`。页面播放标记通过 `playback_indices_in` 按歌曲身份映射，页面重新排序或缺少歌曲不会误用队列索引。
- **播放字段描述不同阶段。** `playback.load.autoplay` 在加载期间保存播放意图，连续切换音质时不能从已停止的设备推断。`playback.started` 在暂停时保持为真；`playback.active_quality` 是实际音质，可能低于持久化的用户偏好。音质解析标记没有读取方，已移除；`ResolvingOptions` 事件仍保留有界通道的发送顺序，以及接收时的列表同步和界面通知。
- **推荐预取与等待续播独立。** `playback.recommendation_loading` 可以在当前歌曲仍播放时为真；只有 `playback.waiting_for_recommendation` 才要求结果到达后从新增歌曲开始播放。
- **历史记录拥有页面资源。** 当前页、历史记录和进行中的请求持有 `Arc`，`PageResourceCache` 只保存 `Weak`。清空前进历史之前先取得目标资源，否则可能失去可复用的最后一个强引用。缓存键包含账号，结果是否属于当前页用 `Arc::ptr_eq` 判断。
- **补页失败保留已有结果。** 搜索的各类别可以同时补页，某类别成功不能清除其他类别的错误；歌手的歌曲、专辑各自结束加载并保留各自的错误。首次搜索成功会清除原搜索错误，歌手请求则在启动前清除对应错误，这些时机不同。请求前的检查还涉及历史页面的可见数量和通知，继续留在页面方法内。
- **分页可被两个用途共享。** 页面补页和播放队列补全通过 `SingleFlight` 共享同一账号、歌单、offset 的请求。资源只追加期望的下一页，避免重复回填。队列切换后，旧任务仍可能补全自己持有的页面资源，但不能覆盖新队列。
- **失效与取消是两件事。** 登录、音乐库、首页、队列和音源加载分别使用版本计数器。它们拒绝晚到的结果，并不会自动终止网络请求。凭据刷新还比较会话身份，防止同一账号的旧会话影响新会话。
- **两套 tick 的寿命不同。** `spawn_in` 的窗口任务更新进度控件；`spawn` 的应用任务在窗口关闭后仍处理曲终与保存。暂停时等待通道唤醒。窗口重开通过 `attach_window` 重建窗口相关同步。
- **歌词有多层缓存。** 原始磁盘缓存、已解析内容、排版结果和当前帧面板各自解决不同问题。已有歌词正在播放时，网络刷新得到的不同内容先进入 `lyrics.pending`，以后选中该曲时采用，避免本次播放中时间轴突然变化。
- **歌词时间和排版不能按字符数简化。** 字范围是 UTF-8 字节下标；没有字级计时的标点和尾部文字借用相邻时间段。QRC 的严格与宽松解析都覆盖真实格式差异，现有测试包含未转义属性和截断输入。
- **自绘和帧率缓存有用途。** 歌词缩放复用已排版字形；进度条用路径避免设备像素取整造成跳动。面板缓存让其他控件重绘时仍遵守歌词帧率限制。`expanded`、`visible`、`fully_expanded` 分别表示用户目标、过渡可见性和跳过底层页面渲染的时机。

网络与阻塞准备任务使用 [runtime.rs](../crates/lyrune/src/runtime.rs) 的共享 Tokio runtime；GPUI 实体通过 `cx.spawn` / `this.update` 接收结果。`drop(RUNTIME.spawn(...))` 让 Tokio 任务继续运行，不能理解为取消。长期维护任务保存 `JoinHandle`，重启维护或实体销毁时显式 `abort`。

## 保留、以后再判断的代码

| 位置 | 当前证据与下一步需要的证据 |
| --- | --- |
| `SearchCardGridDelegate::set_cards` 的参数列表 | Clippy 报告参数过多。参数分别描述数据、布局和分页状态，目前只剩一个调用点；暂未为消除提示引入参数对象，也未关闭提示。后续若布局需要独立复用，再评估其边界。 |

| `AudioCache::prepare_for_seek` | 仅在测试中使用，覆盖跳转 Range 请求且不发送 HEAD 的路径；删除前需要替代这项覆盖，并重新判断 `validate_remote` 的用途。 |
| `LyruneView::shutdown` 的两次保存请求 | `persist_current_playback` 可能提前返回，且仅在播放快照变化时提交设置；后面的 `writer.save` 仍会保存其他偏好，不能直接作为重复调用删除。 |

上述代码仍保留。歌手页原有的多类别卡片函数已确认只有专辑调用，现收窄为 `render_artist_albums`；专辑分支的布局与交互保持原样。搜索页三类卡片共用列表更新流程，各类别仍保留自己的数据、分页状态和卡片高度。歌单和搜索表格使用同一个构造入口，表头高度与内边距保持原值。音质回退、过期结果处理和失败跳歌保持不变；设置的后台保存边界见上文。

另有一项需要单独复现的行为风险：`queue::start_home_recommendation` 回填时只比较推荐类别，未比较账号或请求版本。若旧账号请求跨越退出、重新登录和相同类别的新请求，类别比较可能无法区分结果。需要先用受控的返回顺序确认，再作为行为修复处理，本轮保留基线逻辑。

另一个待复现的原有异常路径在 `lyrics_loading::ensure_track_lyrics`：磁盘旧内容已采用后，若后台任务异常结束而未发送 Network，通道收尾只清理“无已采用内容”的 loading，可能留下该歌曲的加载标记。需要注入受控的任务异常确认，再单独讨论恢复行为；本轮只解释并保留条件。

### 阶段 1：账户规则与任务边界

`Account` 管理登录发起条件、版本失效、当前会话匹配、快照身份和凭据撤销。登录按钮/过期事件调用同一发起规则；凭据刷新与缓存验证共享同一会话匹配规则。未创建通用状态机或重复的登录事件/副作用枚举：二维码成功、过期和失败各自的 UI 编排本身很短且不同，保留直接 `match`。

等价核对：恢复、登录事件分派、凭据保存及两处账户渲染函数与 `6e53150` 完全一致（忽略格式）；账号 ID 调用在归一化所有者路径后也一致。登录发起的状态赋值仍先于通知和任务启动；退出仍依次失效所有版本、停止音频、撤销凭据、清理各领域、保存播放清空结果，最后启动原钥匙串删除任务。

会话谓词等价于“版本相同且当前凭据句柄身份相同”，不读取或修改凭据内容。缓存验证另外保留 `snapshot().is_none()` 检查；这两个本地身份条件在同一次 GPUI 更新内不会改变。刷新监听必须接收当前会话的撤销通知，因此不能把 snapshot 非空加入共用谓词。

新增两个行为测试覆盖恢复/正在登录时禁止重复发起、重试与退出后不复用请求版本、同账号替换会话、会话撤销通知仍可识别以及共享凭据的撤销。定向 2 项通过；完整应用测试 90 通过、2 个真实账号测试仍忽略；应用全部目标编译、格式与差异检查通过。未进行真实登录或钥匙串读写。

### 阶段 2：队列切换与保存快照

结构检查点为 `152c982`。`Playback` 现在统一三个真实队列替换入口的版本失效与推荐状态重置，拥有当前曲、时长、实际播放推进判断和保存快照。搜索插队保持队列版本，退出仍在原跨领域位置使版本失效；音源版本与队列版本继续独立。

由用户在真实桌面、正常音频设备和可用 QQ 音乐账号环境执行。可从项目目录运行 `cargo run --locked -p lyrune`，或使用由当前代码构建的应用。需要比较的行为以 `1320e5d` 为准；本轮没有更换产品行为。网络故障类场景可在日常可复现条件下验证，不需要为本次交接改写真实凭据或缓存。

| 场景和操作 | 预期结果 / 检查重点 |
| --- | --- |
| 启动与登录：分别检查已有有效凭据、没有凭据；扫码、等二维码过期再扫码；失败后点二维码重试 | 恢复成功进入首页并加载音乐库；无凭据进入二维码；过期自动重试，失败保留点击重试和原文案 |
| 退出和重新登录：加载中退出，再登录同一或另一账号 | 已有版本/会话过滤保护新状态，队列清空、保存清空结果；旧凭据监听不能撤销新会话。首批推荐的另案风险见下文，不据此声称全部跨账号路径无缺陷 |
| 导航和后台回填：发起搜索后立即打开其他页面，返回搜索；四种类别分别补页；歌手歌曲和专辑分别补页 | 返回可复用已完成资源，页内可见数量/类别/滚动位置按历史恢复；当前其他页面的控件不会被旧结果覆盖；失败保留已有结果 |
| 歌单与队列：大歌单尚在补全时切换浏览页、再切换播放队列；从搜索插入已有/新歌曲 | 浏览与播放独立；页面可继续得到数据，旧队列任务不能追加新队列；插入不重复已有曲目，保留原同队列补页行为 |
| 播放：快速切歌、加载中切音质、暂停后切音质、拖动进度、切重复/随机模式 | 晚到音源不覆盖最新请求；保留加载期间的播放意图和音质回退；拖动只预览，松开后 seek；错误提示与失败跳歌沿用原规则 |
| 推荐续播：播放接近队尾、等待新的推荐到达；尝试网络失败 | 预取不打断当前曲，队尾等待时从第一首真正新增歌曲续播；失败停止等待并显示原通知，不越界跳歌 |
| 播放恢复：播放到非零位置，正常退出并重新启动 | 恢复对应账号的队列、歌曲、位置和续播信息，加载后保持暂停，手动播放继续；末尾位置按原恢复规则处理 |
| 歌词：有/无磁盘缓存、刷新中切歌、展开/收起、改字体/行距/帧率 | 已有内容先显示；当前曲不同的新内容不在本次播放中突然替换；切歌、UTF-8 逐字高亮、翻译/注音及帧率过渡与原版一致 |
| 设置：改缓存上限、图片容量、历史长度；字体恢复默认后不点应用，再点击应用；重启检查保存 | 各设置按原校验和生效时机处理；字体恢复默认只改输入框，点击应用后生效/保存；设置格式兼容 |
| 窗口与系统：托盘关闭/重开窗口；媒体键或 MPRIS 操作；改变窗口尺寸后正常退出 | 窗口关闭不停止应用播放，重开恢复进度同步；系统媒体状态和休眠抑制跟随原规则；窗口与其他偏好能保存 |

这些步骤覆盖本次改动的主要交互风险，但不宣称替代所有网络故障或硬件组合的集成测试。自动验证能证明纯规则和存储/缓存组件行为，实际 UI、系统会话及账号服务仍须按上表确认。

## 授权与保留判断

内部模块、私有命名、状态分组和生命周期规则的归属使用 Goal 已明确给出的设计授权；未把此前助手的具体方案当作用户指定架构。`AccountState` 的四种语义未变，client_guid 权威来源/空值/协议/存储未触及，没有足够收益引入 typed error，也没有改变同步与异步持久化边界。没有需要用户立即决定的阻塞事项。

保留的复杂代码和以后可能需要的决策：

- 页面/队列共享资源、两套 tick、登录版本与会话身份、歌词延迟采用和多层显示缓存都有现有行为依据，已说明原因。删除它们会改变生命周期或界面表现，不作为冗余处理。
- 数值设置与页面加载独立逻辑占主导，通用抽象会增加参数、分支和间接调用，保持直接流程。
- `set_cards` 参数列表、公共 `playback_url`、缓存 seek 测试路径等保留，所需证据列于 [架构文档](architecture.md)；本轮未凭“当前调用少”删除它们。
- 两项原有异常风险（推荐首批跨账号回填、歌词工作任务异常结束后的 loading）记录为另案；建议先建立受控复现，再决定行为修复。此处不需要现在做产品决策，也未擅自增加新的过滤或重试。

## 必须保留或另案处理的边界

- `CredentialStore` 的钥匙串格式、阻塞线程边界和异步保存/删除时序；不借结构调整改成新的串行写入协议。
- 账户退出对各领域版本号的失效，仍不等于取消网络请求；不得用整个状态对象的默认值重置版本。
- 推荐首批请求仅比较类别、未比较账号/版本的既有风险，见 `architecture.md`；保留基线，行为修复另案。
- 已有 `settings`、`credentials`、`player`、`cache`、`http` 和 QQ 协议 crate 的边界继续保留，除非本轮实际依赖要求局部调整。
- 真实桌面、账号、钥匙串、音频设备及窗口重开验收尚未执行；最终需给出步骤和预期结果。

## 关机条件

系统存在 `/usr/bin/shutdown`，启动时只读查询 login1 `CanPowerOff` 返回 `yes`。沙箱内系统总线访问被限制，只读查询通过工具审批后完成；这不代表未来的实际关机命令已获工具批准。

重构、可执行自动验证和交接文档已完成，人工桌面验收按 Goal 授权交由用户后续执行。保存本报告并完成文档提交后，按授权尝试安排五分钟后的正常关机；实际调度结果以最终回复为准。若权限或会话阻止则报告，不绕过限制；取消已成功安排的关机可运行 `shutdown -c`。
